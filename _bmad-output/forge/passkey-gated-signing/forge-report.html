Per-wallet key setup & passkey-gated signing

Started as "the passkey approves every signature" and became a creation flow where each wallet picks its network, node, how its secret key works, its signature type, and its own checks for opening and for signing.

The threat it targets

Someone using a phone that is already unlocked. It helps somewhat against malicious code in the page, and adds little against stolen device storage, which is already encrypted.

The creation flow

  1. Network: Mainnet / Testnet / Devnet, then the node: pick from the list, or add a custom one with a connection test.
  2. How the secret key works: "Your passkey creates the seed. Same passkey on a new phone = same wallet." or "A new random seed, locked on this phone. A new phone needs your written seed."
  3. Signature type: Ed25519 / secp256k1.
  4. Check when the app opens, per wallet: required on Mainnet (PIN or passkey, auto-lock ≥ 1 min), optional on Testnet/Devnet.
  5. Check on every signature: none, or exactly one of passkey only / PIN only.

Later, outside creation: "Will this wallet be controlled by a master key?" and "Add a passkey as an extra key."

Locked decisions

  • lockA wallet with a signing check has its own seed key, which the session vaultKey cannot open. vaultKey itself stays.
  • lockRevealing the seed requires the same check as signing. Passkey-created seeds can always be revealed, and the screen never says "cannot be exported".
  • lockThe signing PIN is the app PIN. Wrong tries share the unlock screen's count and hard lock, and cancelled passkey prompts never count.
  • lockOne passkey rule everywhere: use an existing passkey or create a new one, named after the wallet, with a separate salt for each use.
  • lockSynced and device-bound passkeys are both allowed. The app states the consequence of the kind it got.
  • lockThe app opens freely. Names are visible, but balances and addresses of locked wallets stay hidden.
  • lockExisting wallets keep working unchanged. Checks can be edited later, but the seed method can't. Weakening a check requires passing it first.
  • lockReverses the mandatory PIN fallback (decisions.md §1): a Mainnet wallet protected only by a passkey requires a confirmed written seed.
  • lockAny wallet can be a master key. If it's on the same phone as the wallet it controls, a plain warning says so. An offline device signs by QR.

Rejected and why

  • rejectedA passkey signature accepted directly by XRPL: the ledger accepts only secp256k1/Ed25519, and WebAuthn signs its own wrapper data.
  • rejectedA passkey prompt while vaultKey can still decrypt the seed: it would be for show only.
  • rejectedA separate signing PIN: easy to forget, and a second lockout to maintain.
  • rejectedAn app-wide open check: it would make "no check on Testnet" meaningless next to a Mainnet wallet.
  • rejectedSplitting keys with a server (MPC), Smart Escrows, Xahau Hooks: no backend, or not a way to authorize an account.
  • parkedlargeBlob (seed inside the passkey): uneven support, no Firefox. If it's ever used, store only the encrypted seed.

Weak points that survived

  • openPasskey-derived keys are tied to the app's domain. A domain change loses them, so the domain is permanent.
  • openOffline QR signing: the default expiry is about 1 minute (20 ledgers). Set it explicitly, e.g. +75 ledgers ≈ 5 minutes.
  • openPer-wallet locks are a real change to the vault, not just a screen.
  • openPre-selected defaults, "turn off master key" (recommend not offering it), and the built-in node list go to the PRD.
