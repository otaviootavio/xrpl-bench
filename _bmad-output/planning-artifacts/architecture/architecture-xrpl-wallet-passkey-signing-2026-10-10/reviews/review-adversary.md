# Adversarial review: ARCHITECTURE-SPINE (passkey signing), 2026-10-10

Method: pairs of units one level down that each satisfy every AD literally and still build incompatibly, checked against PRD 4.14 and `src/lib/crypto/{auth,db,keystore,webauthn,pin,derive}.ts`, `store/app-store.ts`, and `xrpl` Wallet source.

**Verdict: not buildable as written.** Two findings (F1, F2) break a PRD promise or strand funds even with perfect compliance. Seven more are real holes. Several ADs are right in intent and need tightening, not replacement.

## Blockers

### F1. AD-21 "salt generated at creation and stored with the record" defeats FR-62/FR-63 recovery (strands Wallets)
- Pair: *Passkey-Derived Seed creation* vs *recovery on a new phone*. Creation obeys AD-21/AD-24 to the letter: random per-`(walletId,'seed')` PRF salt in the device-local IndexedDB record. A lost or replaced phone keeps the synced passkey but not the salt (or the `walletId`). PRF with an unknown salt yields a different Seed. FR-62 ("same passkey on a new phone = same wallet") is false, and no restore flow exists in any AD or the capability map.
- Constraint tension: FR-70 forbids two Wallets sharing a derivation from one passkey, so the salt cannot be one global constant either.
- Tighten AD-21/AD-24: for `purpose = seed` only, the salt MUST be reconstructible from things the user holds: `salt = SHA-256("xrplbench:seed:v1" || rpId || ordinal)` where `ordinal` is a small integer shown to the user and printed with the written Seed backup, or carried in the credential `user.id` (returned as `userHandle` on assertion). Name a `restorePasskeySeedWallet(ordinal)` operation in `keystore`. Keep "stored, never recomputed from a constant" for `open` and `sign` purposes only, where loss is recoverable by the Seed.

### F2. Migration binds a legacy Wallet to one network, hiding funds on the other (strands Wallets)
- Pair: *migration* vs *new Wallet*. AD-18/AD-19 make identity `(network, address)` and delete the app-wide `network`. Today the same Wallet shows its address on whichever network is selected, and the same address can hold funds on Mainnet and Testnet. AD-27/FR-74 say only "no address changes". Builder A gives each legacy Wallet the persisted app-wide `network` at update time (default `testnet`); builder B duplicates per network. A: a Mainnet-funded Wallet is moved to Testnet by a user who happened to be on Testnet, and its Mainnet funds are unreachable. AD-18 forbids editing network; AD-28 has no such edit.
- Tighten AD-27: migration produces one Wallet record per network the user can see (3 views of one lock/ciphertext, no re-encryption), or a record with `network: 'unbound'` that must be resolved at first open by an explicit choice that never discards the other. Add a test: a vault migrated while the app-wide network was Testnet still opens its Mainnet balance.

## High

### F3. Hard lock as a destructive action triggered at the signing prompt (lockout bypass and a new data-loss path)
- Pair: *PIN path at Open Check* vs *PIN path at Signing Check*. AD-25 shares the count (good) and rewrites `Unlock.tsx` to remove "PIN-dependent Wallets' records". Today the hard lock is reachable only from the unlock screen. Now 8 wrong PINs at any signing prompt, typed by anyone holding an unlocked phone (the stated threat), deletes funded Mainnet Seeds that were never written down. It also arms the attacker's denial-of-funds.
- Second hole: `recordFailure` in `auth.ts` is read-modify-write on `VaultMeta` with no serialization, and the lockout check precedes the attempt. Open-Check and Signing-Check prompts (or two tabs) can run N parallel guesses against one count. The spec's single owner "pin.ts" is not where the count lives today (`auth.ts`/`VaultMeta`), and `auth.ts` is absent from the Structural Seed, so two builders each keep one.
- Third hole: the real `unlockVault` counts a failed *passkey* unwrap, but AD-25 only says wrong PIN counts. Builder A keeps `recordFailure` in the shared unwrap helper and a wrong passkey spends PIN tries.
- Tighten AD-25: (a) the count is incremented in one transaction that also re-checks the limit (compare-and-swap on a counter), and every PIN verification (open, sign, edit, reveal) passes through one `verifyPin(purpose)` in `pin.ts`; `auth.ts` is retired into it. (b) Only a failed PIN verify counts; passkey result kinds never do. (c) Hard lock disables PIN derivation and **deletes nothing**; deletion happens only on an explicit user-confirmed reset that names each Wallet it will remove and shows its written-Seed status. (d) The offline attack is unaffected by the counter (wrapped keys sit in IndexedDB); state that the PIN counter is a UX throttle, not a cryptographic barrier, so no AD or copy claims otherwise.

### F4. "Recoverable through its passkey" has no operation, and legacy Open Check has no literal
- Pair: *hard-lock pruner* vs *Passkey-Derived Seed Wallet with PIN Open Check*. AD-25 says it "remains recoverable" but the Open Key is wrapped under PIN, and the pruner deletes records of PIN-dependent Wallets. The Wallet has no stored Seed, so only a re-wrap of its lock under a passkey brings it back; no AD defines that edit when PIN is disabled (AD-28 requires the *current* check to change a check, which is exactly what the hard lock removed).
- A migrated legacy Wallet's Open Check is PIN **and** passkey (either opens the same key). The Conventions literals offer one of `passkey|pin|none|standard`. Migration writes `pin` (policy then thinks FR-72 does not apply and the pruner deletes a passkey-openable Wallet) or `passkey` (policy applies FR-72 on the next edit and demands a written-Seed ceremony for a Wallet that never asked for it).
- Tighten AD-18/AD-28: `openCheck` is a set (`['pin','passkey']`), policy evaluates over the set, and an edit while the PIN is hard-locked accepts the remaining credential as "the current check". The pruner removes only Wallets whose set is exactly `['pin']` and whose Signing Check is PIN.

### F5. Legacy lock leaves the old ciphertext readable by the session key; AD-27 and AD-28 contradict
- Pair: *migration* vs *edit flow*. AD-27: "a legacy Wallet's `encryptedSeed` is never rewritten in place" (rollback safety). AD-28: an edit "writes the new encryption and removes the old". A builder honouring AD-27 keeps the old `encryptedSeed` for rollback after the Wallet is given a Signing Check. The legacy session key, still held and still persisted in the `session` store for sibling legacy Wallets, then decrypts the "Signing-Check" Wallet's Seed. AD-23's test asserts a path-free property but the remaining record is the path.
- Also: the update waits in the service worker (parent invariant), so an old-build tab and a new-build tab operate on one IndexedDB concurrently. An old-build tab reads the `wallets` store with the session key.
- Tighten AD-23/AD-27: a Wallet that gains a Signing Check has its legacy ciphertext deleted in the same transaction, and rollback loss for that Wallet is stated as accepted (it was already "edited on the new build"). Add: the legacy `wallets` row of such a Wallet becomes a tombstone the old build can only ignore. Add a test iterating every IndexedDB store and asserting no ciphertext decryptable by any session key exists for a Signing-Check Wallet.
- Related backfill trap (algorithm): migration cannot read a legacy Wallet's `algorithm` without decrypting (no re-encryption). If it backfills the default (Ed25519), `Wallet.fromSeed(seed,{algorithm})` for a secp256k1 `s...` seed derives a different key (ripple-keypairs prefers `opts.algorithm` over the seed's own type); `keyAddress` mismatch is then misread as "wrong credential" (AD-24). Tighten AD-18: `algorithm` is optional and absent for legacy Wallets; the signer omits the option when absent.

### F6. Session keys, lazy expiry and teardown do not compose
- Pair: *keystore (per-lock session)* vs *app-store/teardown (per-lock reads)*. AD-21 says "lazy expiry" (checked on use); AD-26 says expiry tears down query data. Nothing fires at expiry, so a Wallet stays rendered and polled after its auto-lock until the next use. Separately, the existing `session` store holds a single record (`key: 'session'`); one builder keeps that record for the legacy lock only, another adds one record per lock, and the refresh-restore code in `auth.ts` restores one and not the other (an unlocked Wallet appears locked, or the reverse).
- Tighten AD-21/AD-26: one named timer owner (`lock.ts`) fires `closeLock(id)` at expiry, which calls teardown. The session store is `session:<lockId>` records, written, extended and cleared only through `lock.ts`. Restore on refresh enumerates them all.

## Medium

### F7. Two owners of Wallet configuration, and a non-atomic creation
- Pair: *creation flow* vs *app-store*. AD-18 says the db record owns config and app-store carries "display meta derived from db". AD-19 says `node` "lives on the Wallet record" while app-store lists `node` as display meta. The client pool reads `node` from whichever the builder finds first. Creation writes db then store in two steps; a crash between them leaves a Wallet in the vault the UI cannot list (or a listed Wallet with no key). Today `listWallets()` derives from the vault, and the store's `wallets` is a persisted copy.
- Tighten AD-18: the store is rebuilt from `db` on every unlock and on every write result (`keystore` returns the meta; nothing else constructs it); store writes are never the first write.
- Creation atomicity: a Passkey-Derived Seed creation involves up to three ceremonies (create/assert seed, open, sign). Edit is atomic (AD-28); create is not. A failure after the first ceremony leaves orphans. Worse, FR-72's written-Seed confirmation can finish after the record is written, so a Mainnet Wallet with a funded address exists unconfirmed. Tighten AD-28: no address is displayed and no record is committed until every ceremony, a verification re-assertion (`keyAddress` equals address derived from the second assertion, as `setUpVaultAuth` already does for the passkey), and the FR-72 confirmation have passed; then one transaction.

### F8. Import from Seed and the legacy keystore surface bypass the new model
- Pair: *import flow (FR-2)* vs *creation flow*. FR-60 excludes import; AD-22 removes only `unlockWalletForSigning`. `importAndStoreWallet(label, seed, vaultKey)`, `generateAndStoreWallet` (returns `seed` to the screen) and `addressFromSeed` still exist and take or imply the session key. An import writes a record with no `lockId`/`openCheck`/`signingCheck`/`keyAddress`; a creation writes all of them. Imported Mainnet Wallets then dodge the Open Check floor (policy never consulted).
- `revealSeed(): Promise<string>` returns the Seed out of `lib/crypto`, contradicting AD-22's own title and CLAUDE.md "no secret in React state". Two builders: one holds the string in state, one in a ref.
- Tighten AD-22/AD-28: `keystore` public surface is closed to exactly `{create, import, signForWallet, revealSeed, editChecks, restore...}`; `import` calls policy and takes the same axes except Seed Method and algorithm; every function that accepts a `CryptoKey` from a caller is deleted. `revealSeed` takes a `sink(seed)` callback invoked once and clears after; the AD states the caller must write to a ref.

### F9. Signing Key can leak through a shared PBKDF2 root and a returned generated key
- Pair: *PIN Open Check* vs *PIN Signing Check*. AD-21: "one PBKDF2 over the PIN, then HKDF per `(id,purpose)`". The obvious optimisation caches the 600k-iteration PBKDF2 bits after the Open Check to avoid a second multi-second derivation at signing. The cached bits derive the `sign` key, so the session can open the Seed. AD-23 says the Signing Key never enters session state but a PBKDF2 root in memory is its precursor.
- Also, a Signing Key must be generated extractable to be wrapped (as `generateMasterKey` is today). A `create` that returns the generated key like `setUpVaultAuth` does hands the caller an extractable Signing Key.
- Tighten AD-21/AD-23: PBKDF2 output and PRF output are cleared in `finally` and never held in a variable that outlives one prompt; the `open` and `sign` derivations each run their own PBKDF2 (own salt per purpose, accepted cost, or Argon2 later); Signing Keys are created, wrapped, and discarded inside one function that returns no key.

### F10. Offline-device QR: unverifiable guards, an undefined comparison, and a keyless Wallet entity
- Pair: *online device* vs *offline device*. (a) AD-13 guards (FR-76/77) read live `account_info`; the offline device cannot, so it either signs with no guard or refuses. The irreversible `AccountSet(asfDisableMaster)` is signed on the offline device, whose confirm text (FR-20) it can only render from the payload. The online device must carry the guard and the payload must be rendered by the offline device from the tx itself, never from a summary field; state that the offline confirm is rendered from decoded tx JSON.
- (b) AD-30: "fields equal what it sent" is undefined. The signer adds `SigningPubKey` and `TxnSignature` (and a Regular Key changes nothing about `Account`); a strict builder rejects every valid blob, a lenient one ignores `Fee`, `Destination`, or `Memos` injection. Define: equal after removing exactly `{SigningPubKey, TxnSignature}`, and recompute and compare the hash.
- (c) The online device needs a Wallet that has no key (address only). No AD models a keyless Wallet: AD-26 hides unlocked-less Wallets' reads, so a watch-only Wallet either never reads or always does. Add a `seedMethod: 'external'` (no lock, no Seed, signing = QR) to AD-18 with its own policy row.
- (d) The offline `signForWallet` must verify `tx.Account` equals the Wallet's Account address (not only `network_id`), otherwise a hostile online device obtains a signature for any Account the key controls.

### F11. Concurrent edits lose updates; "one IndexedDB transaction" cannot span a prompt
- Pair: *edit Open Check* vs *edit Signing Check* (two tabs, or edit vs auto-lock). Both prompt for the current check (async WebAuthn; an IDB transaction auto-commits while awaiting a non-IDB promise), then write the whole record. Last writer wins and the record points at a lock or wrapped key that no longer matches the ciphertext, stranding the Wallet.
- Tighten AD-28: each record carries `rev`; the write transaction re-reads, compares `rev`, and aborts on mismatch (the user retries). The Seed is decrypted and re-encrypted before the transaction opens and only the IDB put/delete happen inside it.

## Smaller notes
- AAD: bind each wrapped key to `(walletId, lockId, purpose)` as AES-GCM additional data so a swapped wrapper fails closed (hardens the AD-24 "wrong credential" story for a malicious-page threat the PRD names).
- rpId: "one constant" makes every passkey ceremony throw `SecurityError` on `dev`/`stage` hosts; say whether the constant is per environment. Migration records `location.hostname` of whichever build runs first, which may be stage.
- A custom Node (AD-20) can lie about `network_id` only once; add a re-check on reconnect, since a Node that passes the test and later switches network would feed a Mainnet Wallet.
- Parent AD-9 compliance for the QR path: the online submit uses `submitAndClassify`, but specify that the "expired" classification uses `LastLedgerSequence` against the validated ledger, not a timer.

## Proposed new/tightened ADs (summary)
1. AD-21 (amend): recoverable `seed` salt; per-purpose PBKDF2; `session:<lockId>` records; timer owner. (F1, F6, F9)
2. AD-27 (amend): migrate per network or unbound; legacy `algorithm` absent; tombstone old ciphertext on leaving the legacy lock. (F2, F5)
3. AD-25 (amend): single `verifyPin` with atomic counter; non-destructive hard lock; passkey failures never count; `openCheck` is a set. (F3, F4)
4. AD-22/AD-28 (amend): closed `keystore` surface incl. import; `revealSeed` sink; atomic create with verification round-trip; `rev` compare-and-swap. (F7, F8, F11)
5. AD-30 (amend): comparison definition; offline `Account` check; keyless Wallet kind. (F10)
