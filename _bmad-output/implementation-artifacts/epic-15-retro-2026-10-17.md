**F1. Story 10 was marked `done` without the verification its own epic requires.** `epics-passkey-signing.md:681` says the master-key action is "verified with real transactions on Testnet before it is marked done". Story 10 is `status: 'done'` with the Testnet check recorded as deferred: "No browser or real-ledger pass: the AccountSet disable and re-enable have only met fakes. The spec's Testnet manual check was not done." (`stories/10-…md`, front matter `deferred`). Stories 8 and 9 shipped the same way (`stories/8-…md`, `stories/9-…md`). The check was later met, on 2026-10-14 and again on `73941df`/`e3d07f4` (`browser-pass-2026-10-14.md:43,45`), so the outcome is fine. The gap was in the ordering, and the unattended loop's `done` did not hold for a criterion that said "before".
- *Disposition:* **accept** for this epic (the check ran, two days later, and passed).
- *Prevention:* a story whose epic text says "verified … before it is marked done" does not take `status: done` from the loop. It stays `review` until the verification section names the run. This is the same shape as the `deferred` "unverified" tags the loop already writes, so the loop can key off them.

**F2. The lockout risk shipped as deferred through three commits.** Story 10 deferred "turn-off needs only a Regular Key set on the ledger; it may be one no wallet on this device can sign with, which locks the funds out" (`stories/10-…md`, `deferred`, severity `medium`), and the stories 9–11 review re-logged it as "High impact" (`deferred-work.md:381-383`). `masterKeyAction` shipped without the check. It was fixed in `73941df` (turn-off refused unless a wallet on this device signs as the Regular Key) and met live in Settings and in the two-device build (`browser-pass-2026-10-14.md:43`).
- This is an irreversible-class action: the epic itself says story 10 is "the only one that can lose funds permanently" (`epics-passkey-signing.md:683`). The story's front matter rated it `medium`; the later review rated it High.
- *Disposition:* **fixed** by `73941df`; the ledger entry is stale (F4).
- *Prevention:* this is exactly what `epic-7-retro-item-18` (hold on a money-moving high finding) and `epic-9-retro-item-30` are for. Both are still `open` (see follow-through). A finding on an action the epic calls irreversible is `high` by definition, regardless of who tagged it.

**F3. The first fix for defect 2 did not work, and its unit test could not see why.** The browser pass found that a send from an Account with the master key off ended as "expired" with no cause named (defect 2, `browser-pass-2026-10-14.md`). `74ab34d` added a choke-point guard, and the re-run on `73941df` showed it **not met**: `SendTab` rebuilt the signing handle as `{ address, open }` and dropped `signsAsMaster`, so the check never ran. The unit test passed the flag directly (`browser-pass-2026-10-14.md:43`). `e3d07f4` spread the handle and added a test that the flag reaches the choke point; the re-run then met it with 0 `submit` frames and an unchanged balance (`:45`).
- This is the same family as the epic 16 lesson (a fake or a direct call hides a wiring gap): a test that supplies an input the real caller never supplies.
- *Disposition:* **fixed** (`e3d07f4`).
- *Prevention:* a guard on the write path is tested from each caller that builds the handle, not only from the choke point. Where the handle is built in more than one place, build it in one.

**F4. The record is stale in two places.**
1. `deferred-work.md:381-383` still lists the master-key lockout as open; `73941df` fixed it.
2. `docs/decisions.md` §15.2 still ends "Not verified against a real ledger: a Testnet disable and re-enable remains to be done" (`docs/decisions.md:1543`). The disable and re-enable were run and recorded (`browser-pass-2026-10-14.md`, row 10, and `:45`).
- *Disposition:* **fix now**, docs only, proposed here and not applied.
- *Prevention:* same as epic 16 F1: the commit that fixes a deferred item or runs a "not verified" check updates the record in that commit.

**F5. Browser defects 6–10 are open, and defect 8 is a defect this retro process already filed.** Defects 1, 2, 4 and 5 were fixed in `74ab34d` (re-run met on `73941df`/`e3d07f4`), and 3 was fixed in `2cc5012` (unit tests; not re-run in a browser). ### Diff-scope review

Scope was narrowed. `bmad-review` was not invoked: each story already had one or two review passes (story 8: 41 and 29 findings; story 9: 32; story 10: 30; `stories/*.md`, Review Triage Log), plus the batched passes `de8d194`…`775ade7`. I read story 8's triage logs and the story 9/10 summaries, and ran the adversarial lens over the epic's **boundaries**: where a story's output is consumed by the next. I did not re-read `EditChecksDialog.tsx`, `keystore.ts` or `ControlWalletDialog.tsx` line by line. The result is "checked on a narrowed scope", not "proven clean".

Boundary observations that hold up against source:
- **Story 9 → story 10.** Story 10's turn-off guard consumes the Regular Key state that story 9 reads from the ledger. The lockout (F2) sat on exactly that boundary: story 9 knew who the Regular Key was, story 10 did not ask whether this device could sign as it. The later guard uses `holdsRegularKeyHere` (`src/lib/master-key.ts`, referenced from `src/lib/two-device.ts:5`), which story 11's two-device path reuses, so the fix is shared, not duplicated.
- **Story 10 → Send.** A master key turned off changes what every other write path may do, and story 10 did not touch the send path. That is defect 2 / F3. A story that changes what the ledger will accept owns the writes that the change breaks.
- **Story 8, one repeated medium theme.** Both review passes patched tests for guards the first pass had no test for (the `others` guard on a shared lock; sealed-to-Standard with an Open Check move; the matched written-Seed path: `stories/8-…md`, follow-up triage). The follow-up commit `b2773cf` is tests only. That is the review loop working, not a defect.

**F6. Three stories carry no real-IndexedDB test of the compare-and-swap.** Story 8's `rev` compare-and-swap is the mechanism that keeps two tabs from losing an edit. The tests run against a fake IndexedDB that "stages a copy, so the in-transaction compare is proven to run but a write between the transaction's read and write is not exercised" (`stories/8-…md`, `deferred`, severity low). A `deferred-work.md` entry also notes that `editChecks` reads the lock twice outside a transaction (`deferred-work.md:372`). The edit rewrites the Seed's ciphertext; losing an update there loses the old key's ciphertext.
- *Disposition:* **defer**, with a `fake-indexeddb` interleave test as the fix; I rate it above `low` because the code it protects replaces the ciphertext of a stored Seed.
- *Prevention:* none beyond the existing `epic-6-retro-item-14` browser-pass rule; a concurrency claim needs a test that can interleave.

### Process lessons

**F7. Stories 8 and 9 carry the `oversized` warning** (`stories/8-…md`, `stories/9-…md` front matter). Story 8's two commits add 2,518 lines in `src` (`git diff --shortstat 49ed6b1..b2773cf -- src`: 14 files, +2518/−201), across the keystore, dialog, policy and database layers. The reviews converged, and story 8's second pass patched no high finding.
- *Disposition:* **accept**; no rework.
- *Prevention:* a story that changes the keystore write path and adds a new dialog splits at that seam.

**F8. The same pattern as epic 16: the loop's own gates passed all three stories, and the live pass found what mattered.** All four gates were green for each story (1121 → 1157 tests, `stories/*.md`, Auto Run Result). The browser pass then found defect 1 (medium-high: a former Regular Key could not be set again) and defect 2. Neither was a unit-test gap in the usual sense: defect 1 was a rule in `eligibleTargets` that excluded any Seed with a stale view "whatever the ledger says" (`browser-pass-2026-10-14.md`, defect 1, confirmed by reading `src/lib/control.ts`).
- *Prevention:* the same as epic 16 action 6: for a story whose behavior depends on a ledger state the tests fake, the live pass runs before the review passes.
