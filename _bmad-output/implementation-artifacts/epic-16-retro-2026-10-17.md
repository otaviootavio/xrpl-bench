### Diff-scope review

Scope was narrowed. `bmad-review` was not invoked: the story already went through two review passes (33 and 35 findings, `stories/11-…md`, Review Triage Log) and a later stories 9–11 pass (`775ade7`). Instead I ran the adversarial and edge-case lenses inline over `two-device.ts`, `qr-codec.ts` and the `writes.ts` diff, weighting the online/offline boundary. **No new code defect was found on that scope.** That is "checked on a narrowed scope", not "proven clean": `TwoDeviceSign.tsx`, `QrScanner.tsx` and the test files were not re-read line by line.

**F2. The scan path, the offline device's main input, has never run on a real camera.** Headless Chromium has no `BarcodeDetector`, so both browser passes used paste (`stories/11-…md`, deferred; `browser-pass-2026-10-14.md`, row 11 and "Not run"). `qr-scanner.test.tsx` (`775ade7`) exercises the camera branch only against a `FakeDetector`. Safari and Firefox lack `BarcodeDetector`, so on those browsers the offline device's only input is a long base64 string (`deferred-work.md`, "Deferred from: code review … stories 9–11", third entry). The choice between a bundled decoder (e.g. jsQR) and stating supported browsers is an owner decision recorded as open there.
- *Disposition:* **defer**, with two parts: run the scan once on a device that has a camera and `BarcodeDetector`; decide the jsQR question.
- *Prevention:* when a feature's main input channel cannot run in the verification environment, the story names which device will run it, so it does not sit as "unverified" through later epics.

**F3. The offline review of `SetRegularKey` shows a bare address.** It carries no "this key can send the account's funds" sentence and does not mention an existing Regular Key that will stop working. Only `master-key-off` has a consequence line. `ControlWalletDialog` says it on the single-device path, and the offline device is where the owner can cross-check least (`deferred-work.md`, stories 9–11 entry, second item). The story did not require it, so this is a gap in the spec rather than a deviation from it. The confirm step (FR-20) is the last gate before a key that can move real funds is signed.
- *Disposition:* **defer**, but it is the one open item that touches real funds on the signing screen, so it should be the first one picked up. It is story-shaped work.
- *Prevention:* a confirm step's spec lists the consequence text per transaction kind, not only the fields.

**F4. The failure paths of the return trip were verified by unit tests only.** The 2026-10-14 pass lists "the tampered-return, wrong-network and wrong-Account QR cases" under "Not run" (`browser-pass-2026-10-14.md:39`). The unit tests use real signatures, so this is weaker than the camera gap, not equal to it. The master-key and Regular Key kinds were exercised live only in the later `73941df` round (`browser-pass-2026-10-14.md:43`).
- *Disposition:* **accept** for this epic; add the three refusals to the next browser pass.
- *Prevention:* none beyond F2's.

### Process lessons

**F5. A defect that made every real return trip fail passed two review passes and 14 round-trip tests.** xrpl.js `autofill` returns `NetworkID: undefined` as a key. `deepEqual` counted it while the JSON payload dropped it, so the first live round trip was refused as "not the one that was sent". The fake `autofill` in the tests did not add that key (`95970aa`; `stories/11-…md`, "Defect found and fixed"; `two-device.ts:316`). Nine test files mention `autofill` (grep over `src/**/*.test.ts*`); I did not check which of them fake it or whether they carry the same gap.
- *Disposition:* **fix now** for the fake: one shared test double whose `autofill` returns the SDK's real field shape, checked once against the real library.
- *Prevention:* for a story that crosses an SDK or wire boundary, the live-ledger pass runs *before* the review passes, not after, since the review passes cannot see what the fake hides.

**F6. Story 11 carried an `oversized` warning** (`stories/11-…md`, front matter): about 2300 added lines across 15 files in one story, covering codec, choke-point additions, the online flow, the offline flow, scanner and dialog. It converged (follow-up pass patched no high, `followup_review_recommended: false`), but the second review found a master-key lockout in code the first pass had already accepted.
- *Disposition:* **accept**; no rework.
- *Prevention:* when a story would add a new `lib` module and a new component tree, split at that seam.
